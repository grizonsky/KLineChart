## Setup
- **Package manager is pnpm only.** `pnpm@10.4.1` is enforced by `scripts/check-env.js` (runs on `install`). npm/yarn will be rejected.
- **Node >= 22** required. CI and `.nvmrc` both use v24.

## Commands

| Task | Command |
|------|---------|
| Install deps | `pnpm install` |
| Lint (src only) | `pnpm code-lint` |
| Type-check | `pnpm type-check` |
| Full build | `pnpm build` |
| JS bundles only (no .d.ts) | `pnpm build-core` |

| Docs dev | `pnpm docs:dev` |
| Docs build | `pnpm docs:build` |

**Build order matters**: `clean -> build-core (esm+cjs+umd) -> build-dts`. Use `pnpm build` for the full pipeline.

## Architecture
- **Single package** at root (no monorepo). `docs/` is a separate Vitepress workspace (`pnpm -F=docs`).
- **Entry**: `src/index.ts` exports `init`, `dispose`, `version`, `register*` functions, and `utils`.
- **Build output**: `dist/` — ESM (`index.esm.js`), CJS (`index.cjs`), UMD (`umd/klinecharts.js` + `umd/klinecharts.min.js`), and `index.d.ts`.
- **`index.js` at root** is the CJS re-export for Node.js (switches between UMD dev/prod). Not the source entry.
- **Build system**: Custom rollup scripts in `scripts/build/`. Config at `scripts/build/config.js`.
- **`__VERSION__`** in `src/index.ts` is a build-time placeholder replaced by rollup. Do not remove it.
- **Zero runtime dependencies** — stated project goal, do not add any.
- **Design system**: See `DESIGN.md` for canvas rendering pipeline, default color palette, candle types, style hierarchy, and extension system.

## Lint & CI
- **ESLint runs during build** with `throwOnError: true` — lint errors will fail the build.
- **`code-lint`** only covers `src/**/*.ts`. Scripts, docs, and config files are excluded.
- **CI** (`.github/workflows/build.yml`): on push to `main` when `src/**` changes — runs `pnpm install`, `pnpm code-lint`, `pnpm build`.
- **Pre-commit hook**: runs `npm run code-lint`.
- **Commit-msg hook**: commitlint with conventional commits. Allowed types: `feat, fix, docs, style, refactor, perf, impr, chore, test, revert, ci, opt, release`.
- **Branch naming convention** (in `scripts/branch-lint.js` but NOT enforced by hooks): `feature/*` or `fix/*` with letters, numbers, hyphens only.

## TypeScript
- Target **ES5**, lib `dom` + `es2018`.
- **Not full strict mode** — only `strictNullChecks`, plus `noUnusedLocals`, `noUnusedParameters`, `noImplicitReturns`, `noFallthroughCasesInSwitch`.
- Types compiled from `src/**/*.ts` only.
- `.d.ts` bundle generated by `dts-bundle-generator` (see `scripts/build/build-dts.js`).

## Working conventions
- Keep responses concise. Start directly with the answer, no filler phrases.
- Before non-trivial changes: present 2-3 approaches with trade-offs, wait for approval.
- Flag uncertainty explicitly — never guess or invent API signatures, function names, or behavior.
- Stay scoped to the task. No auto-refactoring, renaming, or reformatting of unrelated code.
- No temporary fixes — find root causes. If a fix feels like a band-aid, stop and re-evaluate.
- **Financial data awareness**: always account for zero volume, missing klines, division by zero, and floating-point precision issues.
- After changes, run `pnpm code-lint` and `pnpm type-check`.
- This project has no test framework. Discuss whether to add tests or skip per task.

## Planning
- For non-trivial tasks (3+ steps): write a checkable plan before implementing. Confirm with the user.
- If something goes wrong mid-task: stop and re-plan, don't keep pushing.
- When using subagents (`.opencode/agents/`): review output critically before merging. Verify consistency with the codebase.

## Context & Memory
- Consider maintaining `MEMORY.md` with decisions, reasoning, and rejected alternatives for cross-session context. Read it on session start.
- Document repeatedly failed fixes in `ERRORS.md` to avoid retrying proven broken approaches.
- For multi-step tasks, write checkable plans to `tasks/todo.md`.
- Maintain `.docs/dev_docs/` — update `changelog.md` per step, `api.md` when public API changes, `architecture.md` for structural changes.

## Quality bar
- **Confidence markers** on non-trivial decisions:
  - `[WORKS]` — tested logic or well-established pattern.
  - `[UNTESTED]` — reasonable but not verified in this context.
  - `[ASSUMPTION]` — depends on something inferred about the codebase.
  - `[BLOCKED]` — missing specific files, logs, or context to proceed safely.
- Never mark a task complete without proving it works. Define success criteria upfront.
- Before destructive actions (delete, overwrite, dependency changes), stop and ask for explicit `yes`.
- Go fix failing CI/lint issues without being told how.
- If a user question contains a flawed premise, address the flaw explicitly. Don't silently work around it.
- Do not suggest alternative tech stacks unless explicitly asked.
- **Must Never** include secrets, API keys, tokens, or absolute system paths in output.
- **Must Never** submit untested changes. Always verify with `pnpm code-lint && pnpm type-check`.
- **Elegance over hacks**: for non-trivial changes, pause and ask "is there a more elegant solution?". Skip this for simple fixes.
- **One focused task per subagent**. One focused task per subagent call.
- When editing a file, clean up dead code in your path — unused variables, commented blocks. Don't hunt across the project.
